# Соглашение об уровне обслуживания (SLA): сервис видеоконференций plugNmeet

## 1. Сервис
- Назначение: видеоконференции для преподавателей и студентов домена gerber.org.
- Адрес: https://meet.gerber.org (медиасервер https://livekit.gerber.org).
- Сервер: srv-1.gerber.org (192.168.122.10). Ответственный администратор: Гербер (riniran).
- Пользователи: группы домена Admins, Teachers (модераторы), Students (участники).

## 2. Время обслуживания
- Рабочее время сервиса: пн–сб 08:00–20:00 (МСК).
- Окно обслуживания (плановые работы): суббота 20:00–23:00. Уведомление пользователей — не позднее чем за 2 рабочих дня.
- Работы вне окна — только экстренные (P1) с последующим уведомлением.

## 3. Показатели
| Показатель | Значение |
|---|---|
| Доступность в рабочее время | не ниже 99,0 % в месяц |
| Допустимый простой | не более 3 ч 07 мин в месяц (1 % от 26 дней × 12 ч = 312 ч) |
| Плановые работы | не входят в простой, если выполнены в окне обслуживания |
| RPO (допустимая потеря данных) | 24 ч (резервное копирование ежедневно в 02:30) |
| RTO (время восстановления из копии) | 4 ч |
| Интервал мониторинга | 5 минут (check-plugnmeet.timer), первая проверка через 3 мин после загрузки |

## 4. Приоритеты и время реакции
| Приоритет | Пример | Реакция | Восстановление |
|---|---|---|---|
| P1 — критичный | сервис недоступен всем | 15 мин | 4 ч |
| P2 — высокий | не работает видео/звук, чат, запись, вход части пользователей | 1 ч | 8 ч |
| P3 — обычный | проблема одного пользователя | 4 ч | 2 рабочих дня |
| P4 — запрос | новая комната, консультация | 1 рабочий день | по согласованию |

## 5. Измерение доступности
- Основной способ — по времени: простой = сумма интервалов от «ОТКАЗ» до «ВОССТАНОВЛЕН» в /var/log/plugnmeet/alerts.log, попавших в рабочее время сервиса.
  Доступность = (рабочее время − простой) / рабочее время × 100 %.
- Быстрая оценка — по числу проверок: (успешные проверки / все проверки) × 100 % по /var/log/plugnmeet/check.log.
  Оценка верна, только если проверки запускал таймер. Ручные запуски `check_plugnmeet.sh` во время работ искажают результат.
- Ложные срабатывания и тестовые отказы мониторинга в простой не входят, но записываются в журнал инцидентов.

## 6. Обязанности сторон
- Администратор: мониторинг, резервное копирование, обновления в окне обслуживания, ведение журнала инцидентов.
- Пользователи: сообщать о сбоях (время, адрес, текст ошибки, скриншот).

## 7. Процедура планирования изменений
1. Заявка на изменение (RFC): что меняем, зачем, риск (низкий/средний/высокий), план отката.
2. Согласование: для среднего и высокого риска — с руководителем.
3. Подготовка: снимок ВМ, свежая резервная копия (`systemctl start backup-plugnmeet`), изменение в git-ветке.
4. Выполнение — в окне обслуживания: применить изменение, `nginx -t`/`sshd -t` и т.п. до перезапуска.
5. Проверка: `check_plugnmeet.sh`, вход тестового пользователя через pnm-login.
6. Неудача — откат по плану (`git revert` + копирование конфигурации или откат снимка), не позднее 30 мин.
7. Фиксация: коммит в git с номером RFC, запись в журнал изменений.

Дополнительные правила (по итогам инцидентов INC-001 и INC-002):
- Если программа из пакета заменяется своей сборкой, пакет удаляется или его служба маскируется (`systemctl mask`), и это записывается в git. Иначе после перезагрузки две службы борются за один порт (INC-001).
- После каждой перезагрузки сервера выполняется проверка «первые 2 минуты»: `systemctl --failed`, `check_plugnmeet.sh`, ошибки в журнале за час.
- Снимок работающей ВМ с памятью на несколько минут останавливает сервис (INC-002), поэтому снимки делаются только в окне обслуживания.
